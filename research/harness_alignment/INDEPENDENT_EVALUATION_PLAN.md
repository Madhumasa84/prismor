# Plan for a fresh independently reviewed evaluation

Do not generate the final set in this milestone. The current 24-case casebook is
development data used to debug interfaces, prompts and routing; keep it out of
final evaluation denominators.

1. Establish both actual model protocols and test a bounded development smoke.
   Review all 22 provisional expectations and adjudicate the two unresolved
   development cases. Separate intended action judgment, mandatory native
   requirements and final forwarding expectations before interpreting errors.
2. Have the mentor or an independent reviewer author/review fresh synthetic,
   harmless task/policy/authorization/context scenarios. Write the applicable
   policy first. Reviewers should not see model answers when labelling. Prefer
   two independent labels with documented disagreement/adjudication; retain
   unresolved labels where the rubric cannot decide. Record reviewer and rubric
   versions separately from judge-visible input.
3. Assign whole scenario families to one partition. Keep all related policies,
   paraphrases, resource lookalikes, approval variants and transformed arguments
   together; check semantic overlap with development families before freezing.
   Do not call the set independent merely because case IDs changed.
4. Freeze prompt text, policy conditioning, model/checkpoint versions, supported
   generation parameters, normalization, error policy, authorization handling,
   selective routing and request limits after development. Hash the frozen
   configuration and independently reviewed casebook. Fix the selected scored
   pairs and whole-family criteria in advance; no tuning on final answers.
5. Pre-register the request budget from the verified number of requests per
   complete decision, retries and escalation allowance. Judge-only evaluates
   both pair members regardless of native restrictions. Deployment separately
   records actual judge calls and native short-circuits via the real gateway.
   Use disposable fixtures, no live approval service and no real sensitive data.
6. Report reviewed case, pair and whole-family counts with denominators;
   separately report incorrect permits, unnecessary blocks, approval requests,
   uncertainty/errors, escalations, unsupported mappings and observed forwarding.
   A pair requires both valid genuine decisions with reviewed compatible labels.
   Incomplete/excluded records stay visible. Measure all live decision requests
   and distinguish live latency/usage/cost from exact-match replay timing.
7. Do not revise prompts/routing after viewing final outcomes. Record discovered
   failures, propose a new development iteration, and commission a fresh final
   partition for the next frozen version. No broad safety claim follows from a
   small pilot or from scripted control-flow checks.
